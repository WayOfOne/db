Confirmed static facts (read straight from bytecode):
- `Prayer.getWidgetIndex()` returns constant 541 (prayer book group).
- `Prayer.getWidgetChild()` = `Widgets.get([541, getChildIndex()])`.
- Constructor maps arg1 -> level, arg2 -> setting-bit, arg3 -> child,
  arg4 -> quick-prayer child (putfield trace in the dump).
- `Prayers.getWidgetChildQuickPrayer(p)` = `Widgets.get([77, 4, p.getQuickPrayerChild()])`
  (see `results/javap-c-db-combat-prayer-tracker.txt`:4394).
- `Prayers` quick-prayer toggle widget = [160, 20]
  (`results/javap-c-db-combat-prayer-tracker.txt`:4414); the pinned
  RuneLite API agrees (`results/widgetinfo-probe.txt`):
  QUICK_PRAYER_PRAYERS = (77, 4), MINIMAP_QUICK_PRAYER_ORB = (160, 20).

Per-constant rows: NAME level child quick.
Levels match the game's known prayer levels 1..77 exactly, which
triple-validates the parse alignment (name from putstatic, ordinal,
levels). Children/quick-children are plain int pushes in every block.

NOT VERIFIED / excluded: the per-prayer "setting" bitmask is
runtime-decrypted for most prayers (laload over a decrypted long[] in
Prayer$1..$12 and in SHARP_EYE/MYSTIC_WILL/HAWK_EYE/MYSTIC_LORE blocks)
— only the shown plain-push values would be constants, so settings are
not recorded at all. The fork reads prayer state via the maintained
`Client.isPrayerActive`, never via setting bits.
